# 员工设计 · 三方讨论纪要 + 最终方案（单员工 / 多员工）

> 三方：A=产品视角子代理（worker-cognition-ux-polish.md）、B=架构视角子代理（worker-cognition-architecture.md）、C=主设计（本文件综合）。
> 用户重点：**单员工设计 + 多员工设计**；用户立场："我讲的不一定最好，你们三方讨论"。

---

## 0. 三方共识（先立框架）

1. **员工 = Prompt 定义 + 记忆累积 + 进化沉淀**（灵魂/经历/成长三件套）——三方一致。
   - 灵魂（Prompt）：稳定、有版本、可编辑、可回滚
   - 经历（记忆）：只追加、可追溯
   - 成长（进化）：渐进、可撤回
2. **Prompt 三段式**（B 定稿）：`soul`（身份/职责/技能/性格/工作方式/价值观/边界/协作）+ `limits`（预算/权限/红线，引擎强制，员工不能自我授权）+ `meta`（版本/来源）。
3. **进化只提案不改魂**：记忆/技能/习惯可自动沉淀（带证据），人格（identity/persona/values）永远只出提案待用户批准。
4. **信任 = 进化透明**（A 强调，B 认同）：变化必通知 + 证据 + 撤回。

## 1. 单员工设计（一个员工 = 项目的完整灵魂）

### 1.1 核心立场（C 补充，三方认可）
**单员工时，员工"长在项目上"**——项目区就是它的家，它的灵魂/经历/成长就是项目的档案。
用户雇佣一个员工 = 给项目配了一个 7×24 的灵魂。不是"项目里有个工具"，而是"这个项目有个人在守着"。

### 1.2 单员工的完整闭环

```
┌─────────────────────────────────────────────────┐
│           项目区（它的家）                        │
│  ┌─────────┐   ┌──────────┐   ┌─────────────┐  │
│  │ 灵魂档案 │   │ 经历时间线│   │ 成长轨迹     │  │
│  │ 它是谁   │→  │ 它干过啥 │→  │ 它变强了啥   │  │
│  │ prompt  │   │ timeline │   │ growth      │  │
│  └─────────┘   └──────────┘   └─────────────┘  │
│        ↑             ↑                ↑         │
│        └── 7×24 循环（任务→执行→反思→沉淀）──┘   │
│  ┌──────────────────────────────────────────┐   │
│  │ 交互：汇报 / 请示 / 对话 / 教它改习惯      │   │
│  └──────────────────────────────────────────┘   │
└─────────────────────────────────────────────────┘
```

### 1.3 单员工场景下的界面（A 的详情页布局落地）
- 项目区场景里：**一个员工**（像素工位 + 头肩小人 + 状态点 + 任务角标）——他就是主角
- 点击员工 → 详情页：灵魂档案（置顶折叠）+ 概览仪表盘 + 7 tab（经历/技能/习惯/思维/通讯/状态/成长）
- 右侧常驻窄栏：预算进度 / 状态点 / 待审批
- **项目区的知识 = 员工的知识**（单员工时，知识天然共享，无隔离问题）

### 1.4 单员工的关键体验（A 强项）
- **入职确认**：员工复述使命 + 列第一天计划，用户确认才开工（信任起点）
- **"为什么"按钮**：任何行为旁可点 → 思维留痕 + 触发记忆（人话解释）
- **进化通知**：学会技能/形成习惯 → 主动通知 + 证据 + 撤回
- **教它改**：用户说"汇报太啰嗦" → 习惯更新（可追溯）

### 1.5 单员工的工程落地（B 强项）
- 每员工一个独立后台 agent（`ctx.agents.create` + `meta.cwd`），system prompt = `compilePrompt(soul, memoryBundle)`
- 员工目录：`workers/<id>/`（prompt 版本库 + timeline + knowledge + skills + habits + thinking + growth）
- 7×24：schedule/heartbeat 绑定 `employee` 键 → pacemaker 派发到员工 agent

## 2. 多员工设计（团队：分工产生效率，制衡产生质量）

### 2.1 核心立场（C 补充，三方认可）
团队的价值不是"人多"，是两件事：
- **分工**（流水线/并行）= 效率：每个人只干最擅长的一段
- **制衡**（角色并行）= 质量：同一件事多个视角，互查互纠

### 2.2 协作怎么写进员工（A+B 综合）
每个员工 prompt 增加【协作】段（A）+ team 数据结构（B）：
```
【协作】我向谁汇报 / 我从谁接收 / 我的产出交给谁
```
- 流水线：*"你从小码接收代码，产出交给小测；交接必须带测试说明"*
- 层级：*"向主管小维汇报，异常升级给雇主"*
- 独立：*"与同事互不干扰，各自对雇主负责"*

### 2.3 三种团队模式（三方一致，落地为 DAG）

| 模式 | 编排 | 例子 | 场景表现 |
|---|---|---|---|
| 🔗 流水线 | Sequential（链） | 小码写 → 小测测 → 小维部署 | 工位相邻 + 任务流转动画 |
| 🌐 并行分工 | Parallel（扇出） | A 盯服务器 + B 做报告 | 工位分散，各干各的 |
| 🎯 角色并行 | Role-based（同输入多视角） | 同代码：安全+性能+可维护审查 | 多员工围着同一件事 |

**交接物**（B 定稿）：`handoffs/<taskId>.json`（summary/artifacts/acceptance/context ≤500 tokens）——结构化文件传递，不透传会话（防污染）。

### 2.4 记忆隔离 vs 知识共享（A 的洞察，B 落实）
- **经历私有**：每个员工自己的 timeline（隐私隔离）
- **知识共享**：团队级语义记忆（项目事实/规范/约定）——协作的粘合剂
- **交接物流动**：任务上下文随任务走，不共享私密记忆

### 2.5 关系可视化（A+B 综合）
- 场景里：协作箭头 + "任务流转中"状态（小码在写 → 小测在测）
- 团队视图：组织结构图（谁 → 谁，箭头 + 标签：协作/汇报/独立）
- 就位页：选择团队模板 → 自动生成每个成员的【协作】段 + 关系图

## 3. 单 → 多的平滑升级（C 的关键补充，三方认可）

**不是两套系统，是一个系统的两个阶段**：
- 先 1 个员工干着（单员工，它就是项目的灵魂）
- 项目复杂了 → 「＋ 再添加员工」→ 走同样的 prompt 生成
- **新增员工时自动装配【协作】段**：系统检测现有员工 → 生成"你从谁接收 / 交给谁"（如新增测试员：自动接上现有程序员的产出）
- 升级后：原来的单员工自动获得团队位置（它现在有下游了），知识共享开启

**为什么重要**：用户不需要一开始就想清楚要不要团队——先雇一个，需要再加。降低决策门槛，且单/多员工共享同一套灵魂/记忆/进化机制。

## 4. 创建流程最终版（单/多员工两路径）

```
① 说任务 + 确认理解（要点 chips 可改）
        │
② AI 生成员工（档案卡：名字/形象/7 段灵魂，可换一版）
        │
③ 精修灵魂档案（表单+源码双模式编辑器，版本化）
        │   └ 入职配置：工作区/权限/模型/预算（"它被允许怎么活"）
④ 就位 + 入职确认（复述使命 + 第一天计划，确认才开工）
        │
        ├─ 单员工：完成，进入项目区场景
        └─ ＋ 再添加员工：选团队模式（流水线/并行/角色并行）
              → 系统自动装配各成员【协作】段 + 关系图 → 团队就位
```

## 5. 落地优先级（三方共识）

| # | 改动 | 来源 | 为什么 |
|---|---|---|---|
| 1 | 员工目录化 + Prompt Schema/版本管理 | B | 地基：单 JSON 装不下认知系统 |
| 2 | ② 选角色 → AI 生成员工（灵魂档案卡） | A | "prompt 定义员工"的入口 |
| 3 | 每员工独立后台 agent + 派发编译注入 | B | 灵魂生效 + 并行隔离 |
| 4 | 灵魂档案双模式编辑器 + 版本化 | A | 用户真能"改灵魂" |
| 5 | 入职确认（第一天计划） | A | 信任起点，性价比最高 |
| 6 | MemoryBroker 记忆注入 | B | 7×24 连贯性的命门 |
| 7 | 进化透明（变化必通知 + 撤回） | A | 会进化的 AI 最大信任缺口 |
| 8 | 反思循环 + growth 计算 | B | 进化闭环最小可用版 |
| 9 | 团队 DAG 编排 + 协作段 prompt | A+B | 多员工协作落地 |
| 10 | 员工级治理下沉（预算/红线按员工） | B | 多员工安全并存 |

## 6. 待用户拍板的 3 个问题

1. **单员工启动**：默认先雇 1 个员工（它=项目灵魂），团队按需加——认可吗？
2. **团队入口**：在创建向导 ④ 提供"＋ 再添加员工"（选团队模式），还是之后在项目区里加？（建议前者）
3. **进化通知**：员工学会技能/形成习惯时主动通知用户（带证据+撤回）——通知频率怎么定？（建议：技能/习惯类低危自动沉淀+周汇总；人格类必须即时审批）
